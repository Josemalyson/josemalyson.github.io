ESTAÇÃO 01

1. O Harness: o agente além do modelo

Objetivo: Construir o modelo mental correto de Agent = Model + Harness e entender por que o Harness é uma camada de execução, ferramentas, contexto, estado e controle.

Comece pelo limite entre modelo e sistema. O DeepSeek Harness não é apenas uma UI para um LLM: ele organiza as capacidades que fazem um agente operar no mundo. A tese central do projeto é que essas capacidades podem ser trocadas e recompostas como plugins, sem transformar o núcleo do produto em um monólito.

Domínio de saída

Laboratório

Instale o preview localmente, execute o Web UI e registre quais capacidades aparecem no runtime. Depois compare Standard, Code/Programmatic Tool Calling, Minimal e Creator como composições diferentes de capacidades.

2. Cordis: o microkernel de composição

Objetivo: Dominar os conceitos de plugin, Context, service injection, eventos tipados, efeitos reversíveis e composição espacial/temporal.

A segunda estação entra no mecanismo que torna a tese executável. Cordis é o framework sob o Harness. O ponto importante não é apenas 'plugins': é como serviços dependem de outros serviços, como eventos compõem comportamento e como registros são desmontados de forma reversível.

ESTAÇÃO 03

3. Boot, Profiles, Bundles e configuração como composição

Objetivo: Entender como um dsh real vira uma árvore de plugins a partir de profiles, bundles e camadas de patch.

Depois do kernel, a pergunta passa a ser: como o sistema decide quais plugins existem? A resposta é composição declarativa. Profiles agrupam bundles; bundles distribuem linhas de configuração e código; patches substituem ou inserem configurações. A arquitetura deixa de ser 'qual código chama qual código' e passa a ser 'qual árvore de capacidades foi montada'.

Domínio de saída

Laboratório

Execute `dsh --profile web --dump-config`. Escolha uma linha de configuração e desenhe a cadeia: bundle → profile patch → home patch → --patch overlay.

ESTAÇÃO 04

4. O Agent Loop: turn, step, request e tool execution

Objetivo: Reconstituir o ciclo de execução de um agente e localizar os pontos de extensão sem modificar o loop.

Aqui você deixa de pensar no agente como um while-loop abstrato. O Harness possui uma semântica operacional explícita: turn, step, inbox, pre-step, request, streaming, tool calls, resultados e encerramento. Essa precisão é o que permite interceptar comportamento por eventos sem fork do driver.

ESTAÇÃO 05

5. Session Event Sourcing: tudo que o modelo vê é reconstruível

Objetivo: Aprender a sessão como log append-only e entender replay, derivação de histórico, fork, resume e invariantes de reconstruibilidade.

Esta é uma das ideias arquiteturais mais importantes do projeto. A conversa não é armazenada como um histórico paralelo do LLM: ela é derivada de eventos. Isso transforma observabilidade, replay, fork, persistência e UI em projeções do mesmo stream.

Domínio de saída

Laboratório

ESTAÇÃO 06

6. Persistência, crash recovery e replay operacional

Objetivo: Entender como o log em memória ganha durabilidade, batching, recuperação após crash e backends intercambiáveis.

Event sourcing só é útil operacionalmente quando o log sobrevive ao processo. O seam de persistence separa o modelo lógico da estratégia física. JSONL e SQLite podem implementar o mesmo contrato, enquanto flush, recovery e versionamento preservam as propriedades do stream.

7. Capability Seams: ferramentas, políticas, sandbox e modelos

Objetivo: Aprender a projetar capabilities substituíveis com Service Definition, Provider e Consumer e escolher o seam correto para cada comportamento.

Agora a arquitetura vira método de engenharia. Um novo comportamento não deve entrar no loop por conveniência. Você identifica o seam: ctx.tools, ctx.llm, ctx.fs, ctx.sandbox, ctx.subagents, ctx.jobs, ctx.web, ctx.approval e outros. O desenho passa a ser orientado por contratos de capability.

8. Construindo extensões: Tool e LLM Adapter

Objetivo: Passar da leitura arquitetural para autoria real de plugins: registrar uma ferramenta tipada e conectar um novo provider de modelo.

BOSS FINAL

Construa seu próprio Mini Harness

Entrega: um runtime TypeScript mínimo inspirado nas propriedades arquiteturais do dsh, não uma cópia do projeto.

Obrigatórios

  • Context + service registry
  • Plugin mount/unmount com efeitos reversíveis
  • Dependency injection declarativa
  • Eventos tipados com pelo menos um waterfall
  • LLM provider substituível
  • Tool registry com policy hook
  • Append-only session log
  • Replay da execução
  • Teste de teardown sem vazamento de registro

Critério de especialista

  • Você consegue justificar cada seam.
  • Trocar provider não exige editar consumers.
  • Um plugin removido desfaz seus registros.
  • O contexto model-visible é reconstruível pelo log.
  • Policy não depende de modificar o loop.
