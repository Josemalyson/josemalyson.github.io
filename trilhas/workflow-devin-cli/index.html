Começar o lab

Ao final, sem IA, você consegue

Instalar e autenticar o Devin CLI, dirigir um ciclo real de desenvolvimento (planejar, implementar com permissões conscientes, revisar o diff e rodar os testes), deixar regras e uma skill versionadas no repositório, retomar a sessão noutro momento e decidir quando passar o trabalho para o Devin Cloud — e quando não passar. Tudo isso você faz sozinho: a IA do lab não executa no seu lugar.

Ambiente: Terminal na sua máquina (Linux, macOS, WSL ou Windows PowerShell), num repositório de prática criado por você — não use repositório de trabalho. É preciso conta em app.devin.ai e navegador para o login. Não use os modos Bypass, yolo ou dangerous neste lab. O Devin CLI é proprietário; o binário instala de graça, mas o uso depende do plano. No diretório do repositório de prática, inicie o Devin CLI, entre no modo Plan e peça um plano para uma feature pequena (por exemplo, uma nova operação no módulo, com teste). Observe se algum arquivo muda. Você descreve a feature com as suas palavras.

Resultado ilustrativo (da referência, não executado neste lab). Pode variar. Se o seu for diferente, escreva a diferença no campo "O que foi diferente" — isso faz parte do exercício; o lab é corrigido a partir da sua execução real.

Resultado ilustrativo (da referência, não executado neste lab):

A doc de Essential Commands descreve o modo Plan como planejamento somente: o agente propõe mudanças sem fazê-las. Na referência de comandos, o modo Plan usa o profile Plan, com ferramentas somente de leitura (grep, glob, read, todo, ask_user_question, exit_plan_mode), e serve para desenho, entendimento do código e planejamento antes da implementação. git status deve permanecer limpo em relação a arquivos criados ou editados pelo agente.

Plan existe para você pensar o trabalho antes de autorizar escrita. É um profile com ferramentas somente de leitura, não um “modo mais educado” do agente normal. Se o agente tentar editar, recuse a ferramenta e volte ao /plan.

Dica 1Use /plan ou /mode plan. /ask é uma pergunta avulsa sem trocar de modo e também não deveria alterar código.
Dica 2O Shift+Tab cicla modos de permissão (Normal, Accept Edits, Smart, Bypass, Autonomous). Plan e Ask entram pelos slash commands, não por esse ciclo.
SoluçãoNo repo, rode devin, digite /plan, descreva a feature e peça apenas o plano com testes. Ao final, rode git status (dentro ou fora da sessão). Se houver arquivo novo criado pelo agente, o passo não fechou: recuse novas escritas e desfaça o que não pediu.

Objetivo: Fazer o agente implementar o plano, aprovando ferramentas conscientemente e revisando o diff antes de aceitar o resultado.

Saia do Plan com /normal (ou /accept-edits, se quiser auto-aprovar só as edições no workspace). Peça a implementação com testes. Em Normal, leituras passam sozinhas; escrita e shell pedem a sua aprovação. Não use Bypass. Revise o diff e rode os testes você mesmo. Ainda não é obrigatório commitar.

Resultado ilustrativo (da referência, não executado neste lab). Pode variar. Se o seu for diferente, escreva a diferença no campo "O que foi diferente" — isso faz parte do exercício; o lab é corrigido a partir da sua execução real.

Resultado ilustrativo (da referência, não executado neste lab). Segundo a tabela oficial de permissões:

  • Normal (padrão): leitura auto-aprovada; fetch, shell e edições pedem aprovação.
  • Accept Edits: edições no workspace são auto-aprovadas; shell e escritas fora do workspace ainda pedem aprovação.
  • Bypass: tudo é auto-aprovado, inclusive comandos destrutivos — fora deste lab.

Nas aprovações, as teclas 1–4 correspondem a Once, Session, Project e Always, nessa ordem. O critério de pronto deste passo: o diff corresponde ao plano, você o leu, e python -m unittest passa.

Smart auto-aprova edições no workspace e deixa um modelo rápido julgar o resto, mas a doc avisa que pode não estar disponível na sua conta, e categorias de risco (install, git que altera estado, rm, sudo, arquivos sensíveis) continuam pedindo aprovação. Bypass não entra neste lab.

Dica 1No prompt de um comando, a tecla e abre o comando para você editar antes de aprovar.
Dica 2Se o agente seguir por um caminho errado, recuse a ferramenta, interrompa com Esc e corrija o pedido. Se já tiver escrito arquivo demais, use /steps e /revert (você pratica isso no passo 6).
SoluçãoVá para /normal, peça a implementação com testes, aprove leitura implícita e escreva/shell com Once ou Session — evite Always neste lab. Leia git diff, rode python -m unittest e só siga se o resultado for o do plano. Não use Bypass. O commit, se houver, é seu e pode ficar para depois da skill de revisão.

Resultado ilustrativo (da referência, não executado neste lab). Pode variar. Se o seu for diferente, escreva a diferença no campo "O que foi diferente" — isso faz parte do exercício; o lab é corrigido a partir da sua execução real.

Resultado ilustrativo (da referência, não executado neste lab). A doc de Rules diz que o AGENTS.md na raiz é lido automaticamente e é always-on. Nas permissões, deny sempre vence; um allow nunca sobrescreve um deny no mesmo nível. A ordem de precedência (do mais alto para o mais baixo) é: organização/team, grants da sessão, .devin/config.local.json, .devin/config.json, config do usuário.

Preferências pessoais que não devem ir para o time ficam em AGENTS.local.md e .devin/config.local.json, no gitignore. Uma regra de organização (se você estiver num time Enterprise) não é sobrescrita por config de projeto.

Se travar (uma dica por vez; a solução vem por último)

Dica 1O caminho recomendado para regras de projeto é um AGENTS.md curto na raiz, versionado. Instruções concretas (“rode python -m unittest antes de concluir”) funcionam melhor do que pedidos vagos.
Dica 2Em Exec, o prefixo casa como palavra completa: Exec(git) vale para git status, mas não para gitk. Comece o deny por Exec(rm) e Exec(sudo), não por um allow amplo demais.

Passo 07

Criar e invocar uma skill de revisão no fluxo

~25 min repo + sessão CLI

Objetivo: Versionar uma skill reutilizável de revisão de diff e invocá-la você mesmo no fluxo.

Crie .devin/skills/review/SKILL.md com frontmatter e um prompt curto de revisão. Na sessão, invoque /review sobre o diff atual. A skill não deve criar o commit — isso continua sendo seu. O bloco é um esqueleto: preencha as lacunas.

Executei. Revelar o resultado esperado e a explicação

Resultado ilustrativo (da referência, não executado neste lab). Pode variar. Se o seu for diferente, escreva a diferença no campo "O que foi diferente" — isso faz parte do exercício; o lab é corrigido a partir da sua execução real.

Resultado ilustrativo (da referência, não executado neste lab). A skill de projeto vive em .devin/skills/<nome>/SKILL.md (o nome do diretório vira o slash command). Ao invocar, o prompt é injetado na conversa; as ferramentas em allowed-tools são auto-aprovadas; as demais continuam disponíveis e passam pela checagem normal de permissão. Ou seja: allowed-tools não é uma restrição. Para bloquear uma ferramenta numa skill inline, use permissions.deny.

A doc de Skills Overview traz um exemplo de skill review exatamente nesse caminho, com allowed-tools de read, grep, glob e exec, pedindo revisão do git diff.

Skills entram no contexto só quando invocadas (por você ou, se model estiver nos triggers, pelo próprio agente). Por isso a doc de Rules recomenda skills para fluxos repetíveis e AGENTS.md curto. Skills de terceiros podem executar código arbitrário: instale só o que você leu. Neste lab, a skill revê o diff; quem commita é você.

Se travar (uma dica por vez; a solução vem por último)

Dica 1O identificador do slash command é o nome do diretório (.devin/skills/review/ → /review), não só o campo name do frontmatter.
Dica 2Se quiser impedir que o agente invoque a skill sozinho, use triggers: [user]. Para impedir que ela escreva arquivos, coloque a ferramenta de edição em permissions.deny.
SoluçãoCrie .devin/skills/review/SKILL.md com name/description, allowed-tools: [read, grep, glob, exec], permissions.allow para Exec(git diff) e Exec(git log), e um corpo que: (1) rode git diff --staged ou git diff; (2) avalie correção, testes, segurança e estilo; (3) não faça commit nem altere arquivos. Invoque /review, leia o parecer e só então, se concordar, faça o commit você mesmo.

Passo 08

Passar o trabalho ao Cloud e trazer de volta

~25 min terminal

Objetivo: Transferir uma tarefa para uma sessão Devin Cloud e retomar o resultado no seu disco — ou registrar, com base na doc e na sua conta, por que isso está bloqueado.

A doc de handoff afirma que o CLI empacota o contexto da conversa, o repositório, o branch atual e as mudanças não commitadas, e cria uma sessão Cloud que continua daí. A doc de Cloud diz que a sessão roda na VM, portanto fechar o terminal não a interrompe; retome com devin --cloud -r (URL, id ou seletor). /pickup (ou /handoff numa sessão Cloud) busca o branch do pull request da sessão, faz checkout e abre uma sessão local nesse código.

A promoção do SWE-2 até 30/11/2026 não se aplica a sessões Devin Cloud. A página de preços lista acesso a Devin Cloud no plano Pro. Se a sua conta (por exemplo no Free) recusar --cloud ou /handoff, isso é um resultado válido deste passo: registre a mensagem no campo de diferença.

Handoff é o ponto avançado do workflow: o trabalho que não cabe mais no seu laptop (CI, browser, tarefa longa) segue numa VM, e você puxa o branch de volta para o último quilômetro local. Não confunda com o agente local do CLI. Knowledge, Playbooks e Secrets da conta Devin ainda não estão no CLI. Local Hands (a sessão Cloud usar o seu computador), SSH, MCP, plugins, sandbox e DRS ficam fora deste lab; o desafio do fechamento cobre o hook.
