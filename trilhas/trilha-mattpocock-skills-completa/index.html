Premissa: esta trilha foi construída para engenharia reversa operacional do projeto. Ela privilegia fontes primárias: README, CLAUDE.md, CONTEXT.md, plugin.json, SKILL.md individuais e documentação pública do AI Hero.

Mapa operacional

Como o projeto se organiza mentalmente

O projeto funciona como um skill pack de processo: primeiro configura o ambiente, depois roteia a intenção, alinha o problema, formaliza trabalho, executa por feedback loops e revisa contra qualidade e especificação.

Setup /setup-matt-pocock-skills

Configura issue tracker, labels e docs de agente antes dos demais fluxos.

Router /ask-matt

Escolhe o caminho operacional correto: ideia, bug, triagem, arquitetura ou esforço grande.

Alinhamento /grill-with-docs

Entrevista o usuário, cria vocabulário e deixa rastro em CONTEXT.md/ADRs.

Especificação /to-spec

Transforma a conversa em especificação rastreável.

Decomposição /to-tickets

Quebra a spec em fatias verticais com bloqueios explícitos.

Execução /implement + /tdd

Implementa por fatias, guiado por red-green-refactor e revisão.

Review /code-review

Valida Standards e Spec em eixos separados.

Saúde /improve-codebase-architecture

Busca oportunidades de deep modules e redução de bola de lama.

Estação 1 • 18 min

Entender o problema: skills como disciplina de engenharia, não prompts soltos

Separar o projeto de uma biblioteca tradicional: ele é uma coleção de workflows versionáveis para agentes de código.

O primeiro erro seria estudar esse repositório como se fosse um framework. Ele não fornece runtime, API ou componentes reutilizáveis em produção; ele fornece processos operacionais para orientar Claude Code, Codex e outros agentes.

A tese central é que agentes falham menos quando trabalham dentro de loops de engenharia: alinhamento, vocabulário, testes, revisão e decomposição em fatias pequenas. Antes de decorar cada skill, você precisa entender o problema que elas tentam reduzir: desalinhamento, verbosidade, falta de feedback e deterioração arquitetural.

Ao final desta estação, você deve conseguir explicar por que uma skill boa se parece mais com um runbook executável do que com um prompt longo.

Laboratório:
Escreva um mapa de uma página com quatro falhas que o repositório tenta corrigir: desalinhamento, verbosidade, código que não roda e bola de lama arquitetural.
Check de avanço:
Você consegue explicar a diferença entre prompt, skill, workflow e disciplina operacional sem citar uma ferramenta específica?

Estação 2 • 22 min

Instalação, anatomia do repo e contrato de execução

Entender como as skills são instaladas, onde vivem e quais arquivos sustentam o comportamento do agente.

Depois de entender a intenção, você precisa estudar a mecânica. O projeto organiza skills em buckets, promove apenas algumas famílias e usa plugin metadata para expor o conjunto instalável.

O ponto crítico é que a instalação não termina no npx. O setup precisa capturar como o seu repositório trabalha: issue tracker, labels de triagem e localização dos documentos de domínio. Sem isso, as skills downstream começam a adivinhar.

A estação termina quando você souber o que precisa existir em um repo para que as skills rodem de forma previsível.

Laboratório:
Em um repositório sandbox, rode mentalmente o fluxo: instalar skills, selecionar /setup-matt-pocock-skills, definir issue tracker, labels e docs de domínio. Gere uma checklist de arquivos esperados.
Check de avanço:
Você sabe quais decisões são capturadas pelo setup antes do primeiro uso real das skills?

Estação 3 • 25 min

O mapa de navegação: router, fluxos e higiene de contexto

Aprender quando usar cada skill e como o repositório evita perder coerência entre sessões.

A coleção cresce o suficiente para virar um problema de descoberta: você não quer memorizar vinte comandos. O projeto resolve isso com um router: /ask-matt.

A ideia de fluxo é mais importante que a lista de skills. Trabalho novo segue idea → ship; bugs entram por diagnóstico ou triagem; esforços grandes passam por wayfinder; sessões longas exigem handoff em vez de compactação cega.

Aqui você aprende a ler o projeto como um grafo de processos, não como comandos isolados.

Laboratório:
Crie uma tabela com cinco situações reais do seu trabalho e escolha o fluxo: bug intermitente, feature pequena, feature grande, fila de issues, refactor arquitetural.
Check de avanço:
Você consegue decidir quando usar /ask-matt, /wayfinder, /grill-with-docs, /triage ou /diagnosing-bugs?

Estação 4 • 28 min

Alinhamento antes de código: grilling, domínio e ADRs

Dominar a fase de reduzir ambiguidade antes da escrita de spec e antes de qualquer implementação.

A skill /grill-with-docs é o ponto em que o agente deixa de ser executor e vira entrevistador. Ela força decisões, captura vocabulário e atualiza o modelo de domínio do repositório.

O componente mais reutilizável aqui é domain-modeling: termos vagos são desafiados, termos canônicos são criados, contradições com o código são trazidas para a conversa e ADRs são usados apenas quando a decisão é difícil de reverter.

Essa estação deve mudar seu padrão de uso: antes de pedir código, você faz o agente fechar as perguntas certas.

Laboratório:
Pegue uma feature sua e faça um mini /grill-with-docs manual: liste 10 perguntas, 5 termos de domínio, 2 ambiguidades e 1 possível ADR.
Check de avanço:
Você sabe diferenciar fato descoberto no código de decisão que precisa vir do humano?

Estação 5 • 30 min

Da conversa para spec e da spec para tickets verticais

Transformar entendimento em artefatos executáveis: spec, user stories, decisões e tickets com blocking edges.

Depois de alinhar, o projeto evita pular direto para código. Primeiro ele sintetiza o que já foi decidido em uma spec. Depois quebra a spec em tickets verticais que atravessam camadas e podem ser verificados individualmente.

O conceito chave é tracer bullet: uma fatia estreita que prova o caminho end-to-end. Isso se opõe a slicing horizontal, onde schema, API e UI são feitos separadamente e nada fica demonstrável até o fim.

Ao final, você deve conseguir pegar uma feature complexa e gerar issues que um agente consiga implementar sem reabrir decisões.

Laboratório:
Escolha uma feature simples e escreva: problema, solução, 8 user stories, decisões de implementação, decisões de teste, fora de escopo e 5 tickets com blockers.
Check de avanço:
Você consegue quebrar uma feature em tickets verticais sem cair em 'fazer todo backend' e depois 'fazer todo frontend'?

Estação 6 • 32 min

Execução: implement, TDD, diagnóstico e loop de feedback

Aprender o loop que transforma tickets em código com testes, typecheck e regressão.

A implementação é deliberadamente estreita: a decisão sobre o que construir já aconteceu. O agente deve trabalhar a partir de spec ou tickets, usar seams pré-acordados, rodar typecheck e testes continuamente e só fazer o sweep completo no final.

O TDD aqui não é uma cerimônia; é um mecanismo de feedback para agentes. O teste deve verificar comportamento em interface pública, não detalhes internos. Diagnosing-bugs aplica a mesma lógica: antes de hipótese, criar um loop tight que reproduz o problema.

O objetivo é tirar o agente do modo 'eu acho' e colocá-lo no modo 'um comando prova'.

Laboratório:
Crie um ticket mínimo e defina um seam público, um teste red, o comando de teste unitário, o comando de typecheck e o comando de suite final.
Check de avanço:
Antes de implementar, você consegue nomear o seam testado e o comando que ficará vermelho se o comportamento estiver quebrado?

Estação 7 • 34 min

Review e saúde arquitetural: standards, spec e deep modules

Usar code-review e codebase-design para impedir que velocidade com IA vire entropia arquitetural.

A cadeia não termina quando os testes passam. O projeto separa review em dois eixos: standards e spec. Isso impede que código bonito mas errado, ou correto mas fora dos padrões, passe sem explicitar o problema.

A camada arquitetural usa vocabulário próprio: module, interface, seam, adapter, depth, leverage e locality. O objetivo é desenhar módulos profundos, com muito comportamento atrás de uma interface pequena e testável.

Essa estação conecta diretamente com seu loop de pre-commit e TAAC: o agente precisa fechar a mudança com verificação técnica e revisão sem misturar critérios.

Laboratório:
Pegue um diff real e faça uma review em dois blocos: Standards e Spec. Depois identifique uma oportunidade de deepening usando deletion test.
Check de avanço:
Você consegue separar achados de conformidade de padrões, achados de aderência à spec e achados de desenho arquitetural?

Estação 8 • 36 min

Adaptar para seu ecossistema: escrever skills previsíveis e operar em múltiplas sessões

Extrair princípios para criar suas próprias skills no padrão HES/SDD sem copiar cegamente o repo.

A etapa final é engenharia reversa aplicada. Você não quer apenas usar as skills do Matt; quer absorver o padrão para criar suas próprias: pequenas, composáveis, com critérios de conclusão e progressiva divulgação de referência.

writing-great-skills é a peça mais importante para seu projeto de cultura de AI: ela define previsibilidade, context load, cognitive load, router skill, leading words, no-op, sediment e sprawl. Handoff, research e teach mostram como preservar contexto, delegar leitura e aprender ao longo de sessões.

O resultado final esperado é você conseguir criar um skill pack próprio para sua empresa, com setup, roteador, fluxos e gates de qualidade.

Laboratório:
Crie uma versão inicial de um skill pack corporativo: /ask-jose, /setup-org-skills, /to-spec, /to-tickets, /implement-taac, /review-taac, /handoff.
Check de avanço:
Você consegue explicar quais skills devem ser user-invoked, quais podem ser model-invoked e por quê?

Fixação

Plano prático de 7 dias

  1. Dia 1Leia README, CLAUDE.md e plugin.json. Faça o mapa mental de buckets e invocação.
  2. Dia 2Instale em um repo sandbox e execute /setup-matt-pocock-skills.
  3. Dia 3Simule uma feature pequena usando /ask-matt → /grill-with-docs → /to-spec.
  4. Dia 4Quebre a spec com /to-tickets e valide se cada ticket é vertical e desbloqueável.
  5. Dia 5Implemente um ticket com /implement e force o loop /tdd.
  6. Dia 6Rode /code-review e compare falhas de Standards versus falhas de Spec.
  7. Dia 7Escreva uma skill própria baseada no fluxo TAAC/pre-commit loop e valide contra writing-great-skills.

Boss Final

Sem gabarito. Responda por escrito para provar retenção, síntese e capacidade de adaptação.

  1. 1. Conceitual

    Por que mattpocock/skills é melhor entendido como sistema de workflow e não como biblioteca de código?

  2. 2. Arquitetura

    Qual é a diferença operacional entre /grill-with-docs, /to-spec e /to-tickets?

  3. 3. Fluxo

    Quando você escolheria /wayfinder em vez de /grill-with-docs?

  4. 4. Qualidade

    Por que /implement não deve decidir o que construir durante a implementação?

  5. 5. TDD

    O que torna um teste bom nesse projeto: testar internals ou testar comportamento em seam público?

  6. 6. Review

    Por que a review é separada em Standards e Spec? Dê um exemplo de falha em cada eixo.

  7. 7. Domínio

    Quando uma decisão merece ADR e quando deve ser apenas vocabulário em CONTEXT.md?

  8. 8. Customização

    Como você adaptaria esse sistema para um fluxo corporativo com TAAC, pre-commit loop e múltiplos agentes?
