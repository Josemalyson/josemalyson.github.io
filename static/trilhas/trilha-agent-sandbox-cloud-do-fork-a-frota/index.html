Fase 1 · Estação 01

Por que agentes precisam de um computador isolado

~18 min de leitura2 nervo(s)

Objetivo. Conectar tool calling, execução de código e recompensa verificável à necessidade de uma fronteira de confiança explícita.

O que dominar

  • O harness traduz pedidos do modelo em ações de shell, arquivos, navegador ou ferramentas.
  • Código gerado é não confiável mesmo quando não há intenção maliciosa: bugs, dependências e comandos amplos também causam dano.
  • A sandbox é um ambiente com capacidades deliberadamente concedidas; não é apenas “um Docker”.

Laboratório. Modele um agente mínimo que pede ao harness para executar um cálculo, recebe stdout/stderr e decide se precisa tentar novamente. Nesta estação, o executor ainda é um processo local descartável.

Entregável. Diagrama do loop agente → tool call → executor → observação → grader/usuário, com o ponto exato onde entra a sandbox.

Armadilhas

  • Confiar no prompt como controle de segurança.
  • Misturar a lógica do agente com privilégios de infraestrutura.
  • Tratar saída textual como único resultado; o estado do computador também é saída.

Fase 1 · Estação 02

Requisitos distintos: pesquisa versus produto

~16 min de leitura2 nervo(s)

Objetivo. Derivar SLOs de throughput, latência, confiabilidade, segurança e custo para dois tipos de carga.

O que dominar

  • Pesquisa favorece muitos rollouts paralelos, alta utilização e repetibilidade estatística.
  • Produto favorece cold start baixo, interação responsiva, persistência e isolamento entre usuários.
  • Falhas desperdiçam tokens/GPU em ambos os lados; disponibilidade da sandbox é parte da qualidade do agente.

Laboratório. Crie duas fichas de SLO: uma para 50 mil rollouts/hora e outra para sessões interativas de 30 minutos. Defina p50/p95/p99, taxa de criação, erro, recuperação e orçamento.

Entregável. Tabela de SLOs e prioridades, incluindo quais métricas entram no admission control.

Armadilhas

  • Usar um único pool e uma única política para treinamento e produto.
  • Otimizar boot sem medir tempo até a primeira ação útil.
  • Ignorar custo de snapshots, rede e armazenamento.

Threat modeling: ativos, adversários e fronteiras

~24 min de leitura2 nervo(s)

Objetivo. Construir um modelo de ameaça específico para agentes autônomos, sem depender de controles vagos.

O que dominar

  • Ativos: host, control plane, credenciais, dados de outros tenants, imagens, snapshots e evidências de auditoria.
  • Ameaças: privilege escalation, kernel escape, exfiltração, DoS, lateral movement, confused deputy e supply-chain compromise.
  • A garantia final é limitada pelo elo mais fraco entre runtime, rede, identidade, storage e orquestração.

Laboratório. Execute uma sessão STRIDE/LINDDUN simplificada. Para cada fluxo do diagrama, registre ativo, ameaça, precondição, impacto, controle preventivo, controle detectivo e risco residual.

Entregável. THREAT_MODEL.md com trust boundaries e uma matriz de risco priorizada.

Armadilhas

  • Modelar apenas escape do guest.
  • Esquecer o operador, APIs internas e snapshots como superfícies.
  • Classificar “microVM” como mitigação universal.

Fase 2 · Estação 05

Linux por primeiros princípios: threads, syscalls e privilégios

~26 min de leitura2 nervo(s)

Objetivo. Entender a transição user space/kernel space e distinguir UID 0 de execução em ring 0.

O que dominar

  • Threads executam em user space e solicitam operações privilegiadas por syscalls ou ioctls.
  • Root amplia permissões no sistema operacional, mas permanece em user mode; um exploit de kernel altera a fronteira inteira.
  • VMMs usam ioctls de KVM para criar VMs e vCPUs, mas continuam processos que precisam ser confinados.

Laboratório. Use strace em um programa simples para classificar syscalls de processo, filesystem, rede e memória. Não execute payloads ofensivos; o objetivo é mapear dependências.

Entregável. Catálogo de syscalls requeridas pelo seu executor mínimo e indicação de quais podem ser removidas.

Armadilhas

  • Achar que “não executar como root” elimina kernel exploits.
  • Bloquear syscalls sem observar compatibilidade real.
  • Dar ao executor acesso direto ao socket do runtime/container manager.

Fase 2 · Estação 06

Baseline fork/exec: o caminho mais rápido e mais perigoso

~18 min de leitura2 nervo(s)

Objetivo. Implementar a baseline nativa para medir desempenho e revelar suas falhas de segurança e vizinhança.

O que dominar

  • fork/exec oferece latência mínima e compatibilidade máxima porque executa processos normais do host.
  • Sem limites, fork bombs, loops, consumo de memória e descritores afetam toda a máquina.
  • O executor herda filesystem, rede, environment e privilégios do serviço que o iniciou.

Laboratório. Implemente um worker com timeout, limite de output, diretório temporário e kill da árvore de processos. Use apenas comandos benignos e testes de consumo controlado.

Armadilhas

  • Matar apenas o processo pai.
  • Confiar em timeout sem limitar PIDs, memória e I/O.
  • Executar como o mesmo usuário do control plane.

Fase 2 · Estação 07

Namespaces: visões isoladas de recursos globais

~25 min de leitura2 nervo(s)

Objetivo. Compreender PID, mount, network, user, IPC, UTS, cgroup e time namespaces como peças independentes.

O que dominar

  • Namespaces mudam a visão de recursos; eles não virtualizam o kernel.
  • User namespaces permitem mapear identidades internas para UIDs externos menos privilegiados.
  • Mount propagation, procfs e dispositivos mal configurados podem romper expectativas de isolamento.

Laboratório. Em uma VM descartável, use unshare para criar namespaces de PID, mount e user; inspecione /proc de dentro e de fora. Mantenha a rede desconectada no primeiro experimento.

Entregável. Mapa “recurso → namespace → risco se compartilhado → teste de verificação”.

Armadilhas

  • Montar /proc ou /sys sem considerar a visão do namespace.
  • Usar host network ou host PID por conveniência.
  • Assumir que namespace de usuário é idêntico a uma VM.

cgroups v2: CPU, memória, PIDs e I/O como contrato

~24 min de leitura2 nervo(s)

Objetivo. Transformar limites de recursos em invariantes verificáveis por sandbox e por tenant.

O que dominar

  • cpu.max controla quota; memory.max e memory.high diferenciam hard limit e pressão; pids.max contém explosão de processos.

Armadilhas

  • Definir apenas requests sem hard ceilings.
  • Interpretar OOM como erro genérico.
  • Não reservar recursos para host, VMM e serviços de controle.

Fase 2 · Estação 09

Hardening de containers: mínimo privilégio e LSMs

~30 min de leitura3 nervo(s)

Objetivo. Montar uma baseline defensiva para quando containers forem suficientes ao modelo de ameaça.

O que dominar

  • Remover capabilities, usar UID não-root, rootfs read-only, no_new_privs e dispositivos mínimos.
  • Seccomp reduz syscalls; AppArmor/SELinux/Landlock restringem objetos e caminhos; os controles são complementares.
  • A política deve ser testada contra workloads reais e versionada como código.

Laboratório. Crie um perfil OCI restrito, execute uma suíte de compatibilidade e registre cada exceção como ADR. Não adicione modo privileged para “fazer funcionar”.

Entregável. Container hardening profile, testes positivos/negativos e inventário de exceções.

Armadilhas

  • Usar seccomp unconfined.
  • Montar docker.sock, /dev/kvm ou diretórios do host sem mediação.
  • Conceder CAP_SYS_ADMIN, que agrega muitas operações sensíveis.

Fase 3 · Estação 11

KVM e VMX: a fronteira assistida por hardware

~30 min de leitura2 nervo(s)

Objetivo. Entender por que guest ring 0 não equivale a host ring 0 e como KVM participa da execução.

O que dominar

  • O guest executa em contexto de virtualização separado; operações sensíveis causam VM exits.
  • KVM fornece o mecanismo no kernel; o VMM constrói memória, vCPUs, devices e lifecycle.
  • A TCB inclui hardware, KVM, VMM e backends de device; a VM não elimina a necessidade de hardening.

Laboratório. Verifique /dev/kvm, leia capabilities da API e construa um diagrama de criação de VM sem ainda iniciar código não confiável.

Entregável. Sequência de chamadas: open /dev/kvm → create VM → map memory → create vCPU → KVM_RUN.

Armadilhas

  • Chamar KVM de VMM.
  • Expor /dev/kvm diretamente ao código do agente.
  • Ignorar side channels e bugs de device emulated.
