Construir todos os servicos de um cluster EKS com add-ons e workloads de producao

Objetivo

Ao final, voce conseguira reconstruir um cluster EKS semelhante ao inventario da imagem: add-ons de plataforma como AWS Load Balancer Controller, Datadog, External Secrets, Fluent Bit, Metrics Server, KEDA, Falcon KAC e Argo Rollouts; e workloads internos como timeline-mobile-bff, timeline-adapter-gateway, hub-account-*, quickconfig e org-yy4-*. O foco e pratico: IaC, Helm, CRDs, IAM, rede, observabilidade, autoscaling, seguranca e rollout progressivo.

Do print ao contrato de plataforma: inventariar o cluster

~8 min leitura 4 nervos

A imagem mostra uma mistura tipica de plataforma e produto: namespaces de add-ons, webhooks, APIs internas e BFFs expostos como ClusterIP. No nivel avancado, o primeiro passo nao e instalar coisas; e transformar kubectl get svc -A em um contrato operacional: o que e add-on, o que e workload, qual porta e usada, quem depende de quem e qual falha derruba o fluxo do usuario.

Nervos validados

  • Service | Kubernetes

    Kubernetes Docs · leitura profunda

    Quando seguir: antes de replicar os ClusterIP da imagem.

    Validado: cobre ClusterIP, NodePort, LoadBalancer e ExternalName.

  • DNS for Services and Pods

    Kubernetes Docs · leitura profunda

    Quando seguir: para entender como timeline-mobile-bff-service.timeline-mobile-bff.svc deve resolver internamente.

    Validado: explica DNS estavel para Services e Pods.

  • Kubernetes Services Explained

    Video · ClusterIP, NodePort, LoadBalancer

    Quando seguir: se quiser consolidar visualmente a diferenca entre os tipos de Service.

    Validado: a descricao cobre os tres tipos principais de Service.

  • Kubernetes at Uber, with Lucy Sweet

    Kubernetes Podcast · publicado em junho de 2026

    Quando seguir: para captar o peso operacional de DNS e inventario em escala real.

    Validado: show notes citam migracao para Kubernetes, escala e DNS.

Entrega pratica

Gere um CSV a partir de kubectl get svc -A -o json com namespace, servico, tipo, portas, owner provavel, criticidade e dependencia. Classifique cada linha da imagem como plataforma, observabilidade, seguranca, autoscaling, rollout ou produto.

Construir a base EKS com Terraform, add-ons e padroes de operacao

~9 min leitura 4 nervos

Um cluster que roda Datadog, External Secrets, KEDA, Falcon e Argo Rollouts precisa nascer com decisoes explicitas: versao, VPC, subnets, endpoints, node groups, add-ons gerenciados, quem instala CRDs, quem possui Helm releases e qual fluxo promove mudancas. Aqui voce sai do console e monta uma fundacao reprodutivel.

Nervos validados

  • Amazon EKS Best Practices Guide

    AWS Docs · day-2 operations

    Quando seguir: para transformar instalacao em padroes de operacao.

    Validado: guia oficial de praticas para day-2 em EKS.

  • terraform-aws-eks

    Terraform module · IaC

    Quando seguir: para criar cluster, node groups e configuracoes EKS sem clicar no console.

    Validado: README referencia managed node groups, self-managed node groups e Fargate.

  • EKS Blueprints Addons

    AWS IA · Terraform + Helm

    Quando seguir: para padronizar add-ons como LBC, External Secrets, KEDA e Argo.

    Validado: modulo declara deploy de Kubernetes add-ons em EKS.

  • Amazon EKS add-ons

    AWS Docs · add-ons gerenciados

    Quando seguir: para decidir entre EKS managed add-on e Helm chart externo.

    Validado: cobre add-ons de observabilidade, rede, storage e seguranca.

Entrega pratica

Monte um esqueleto Terraform com VPC, EKS, node group, add-ons gerenciados essenciais e um modulo de add-ons Helm. Registre no README quais componentes serao gerenciados pela AWS e quais serao gerenciados por Helm/GitOps.

Rede interna: VPC CNI, Services, DNS, portas e capacidade de IP

~10 min leitura 4 nervos

Os ClusterIP da imagem parecem simples, mas em EKS eles descansam em cima do VPC CNI, ENIs, subnets, CoreDNS, kube-proxy e regras de seguranca. Esta estacao te ensina a criar a rede para suportar densidade de pods, resolver nomes internos e evitar que uma decisao de subnet vire falha de deploy.

Nervos validados

  • Amazon VPC CNI best practices

    AWS Docs · networking

    Quando seguir: antes de escolher instancias, prefix delegation ou subnets para pods.

    Validado: explica ENIs, warm pool e slots de IP.

  • EKS Workshop: Prefix Delegation

    AWS Workshop · lab pratico

    Quando seguir: para testar aumento de densidade de pods em nodes Nitro.

    Validado: lab orienta prefixos no Amazon VPC CNI.

  • Ingress | Kubernetes

    Kubernetes Docs · L7 routing

    Quando seguir: para separar service discovery interno de entrada HTTP externa.

    Validado: define regras por URI, host e path.

  • HN: EKS, Bottlerocket, managed add-ons e Karpenter

    Hacker News · sinal de comunidade · marco de 2026

    Quando seguir: como termometro de escolhas reais em EKS, nao como fonte normativa.

    Validado: comentario cita EKS com Bottlerocket, add-ons gerenciados e Karpenter.

Entrega pratica

Crie namespaces e servicos mock para timeline-mobile-bff, timeline-adapter-gateway, hub-account-* e quickconfig. Rode testes de nslookup, curl, NetworkPolicy basica e consumo de IP antes/depois de prefix delegation.

Identidade e segredos: Pod Identity, IRSA e External Secrets

~10 min leitura 4 nervos

external-secrets-webhook aparece na imagem porque segredos sao parte do plano de controle do seu produto. A meta aqui e eliminar secrets hardcoded, criar permissoes IAM por service account, entender quando usar Pod Identity ou IRSA e publicar segredos no cluster sem vazar valor sensivel no Git.

Nervos validados

  • EKS Pod Identities

    AWS Docs · IAM para workloads

    Quando seguir: para workloads novos que acessam AWS APIs.

    Validado: cobre least privilege, isolamento de credenciais e associacao por service account.

  • IAM roles for service accounts

    AWS Docs · IRSA

    Quando seguir: quando seu padrao atual ainda usa OIDC e anotacao no ServiceAccount.

    Validado: documenta roles IAM associadas a service accounts Kubernetes.

  • EKS Workshop: External Secrets

    AWS Workshop · lab pratico

    Quando seguir: para ligar AWS Secrets Manager ao cluster.

    Validado: lab cria ClusterSecretStore referenciavel por namespaces.

  • ESO Security Best Practices

    External Secrets Operator · seguranca

    Quando seguir: antes de liberar ClusterSecretStore amplo em producao.

    Validado: aborda NetworkPolicies e risco de exfiltracao.

Entrega pratica

Crie um segredo em AWS Secrets Manager para timeline-mobile-bff, associe permissao por Pod Identity ou IRSA ao External Secrets Operator, publique um ExternalSecret no namespace da app e prove que o valor nao aparece no Git.

Entrada de trafego: AWS Load Balancer Controller, ALB, NLB e webhooks

~10 min leitura 4 nervos

A imagem mostra aws-load-balancer-controller e seu webhook. Este componente traduz Ingress e Service em ALBs/NLBs, mas tambem adiciona webhooks, IAM, CRDs e risco operacional. Voce precisa entender annotations, target types, cert-manager, health checks e falhas de webhook antes de expor qualquer BFF.

Nervos validados

  • Install AWS Load Balancer Controller with Helm

    AWS Docs · tutorial/lab

    Quando seguir: para instalar o controller do jeito suportado em EKS.

    Validado: guia inclui IAM role, instalacao Helm e verificacao do Deployment.

  • Route HTTP traffic with Application Load Balancers

    AWS Docs · ALB ingress

    Quando seguir: para expor BFFs por host/path.

    Validado: explica target-type ip e registro de Pods no ALB.

  • AWS LBC Ingress annotations

    Controller docs · annotations

    Quando seguir: para modelar TLS, health check, target group e scheme.

    Validado: lista annotations aplicaveis a Ingress e Service.

  • AWS LBC releases: Gateway API e webhook TLS

    GitHub releases · sinal recente · 2026

    Quando seguir: para aprender a ler release notes antes de atualizar add-ons.

    Validado: release v3.0.0 cita Gateway API GA e acao em CRDs/webhook.

Entrega pratica

Instale o AWS Load Balancer Controller com IAM dedicado. Publique um Ingress para dois BFFs mockados, um Service LoadBalancer NLB para trafego TCP e um checklist de troubleshooting para falha em aws-load-balancer-webhook-service.

Autoscaling: Metrics Server, HPA, KEDA e capacidade com Karpenter

~10 min leitura 4 nervos

A imagem tem metrics-server, keda-operator, keda-admission-webhooks e keda-operator-metrics-apiserver. Isso indica duas camadas: escalonar replicas com metricas e eventos, e garantir que o cluster tenha nodes certos para acomodar os pods.

Nervos validados

  • Kubernetes Metrics Server

    Kubernetes SIGs · metrics API

    Quando seguir: antes de configurar HPA por CPU/memoria.

    Validado: expõe resource metrics para HPA, VPA e kubectl top.

  • Event-driven autoscaling with EKS Pod Identity and KEDA

    AWS Prescriptive Guidance · lab

    Quando seguir: para escalar workers por SQS sem credenciais estaticas.

    Validado: usa TriggerAuthentication, ScaledObject, SQS e escala para zero.

  • Karpenter best practices for EKS

    AWS Docs · cluster autoscaling

    Quando seguir: para escolher NodePools, constraints e consolidacao.

    Validado: descreve NodePools, taints, labels, requirements e limites.

  • KEDA, with Tom Kerkhove

    Kubernetes Podcast · audio com show notes

    Quando seguir: para entender por que KEDA complementa HPA.

    Validado: show notes citam superpowers para HPA e scale zero-to-one.

Entrega pratica

Instale Metrics Server e KEDA. Configure HPA em um BFF HTTP e ScaledObject SQS em um worker. Em seguida, crie um NodePool Karpenter com limites e demonstre escala de pods e escala de nodes sob carga.

Seguranca e entrega progressiva: Falcon KAC e Argo Rollouts

~10 min leitura 4 nervos

O print mostra falcon-kac e argo-rollouts. Isso fecha o ciclo: bloquear ou observar objetos inseguros antes de entrarem no cluster, e trocar versoes de produto com canary/blue-green em vez de rollout cego. O nivel avancado esta nos modos de falha: webhook indisponivel, metricas ruins, health checks lentos e rollback mal definido.

Nervos validados

  • Falcon Kubernetes Admission Controller Helm Chart

    CrowdStrike GitHub · Helm

    Quando seguir: para instalar o falcon-kac visto na imagem.

    Validado: README define KAC como plugin para revisar objetos criados.

  • Argo Rollouts docs

    Argo Project · progressive delivery

    Quando seguir: para trocar Deployment por Rollout em apps criticas.

    Validado: cobre blue-green, canary, analysis e experiments.

  • Argo Rollouts with AWS Load Balancer Controller

    Argo docs · lab com ALB

    Quando seguir: para canary real em EKS usando ALB.

    Validado: guia declara integracao com AWS LBC para traffic shaping.

  • Supercharge Your Canary Deployments With Argo Rollouts Step Plugins

    Video · publicado ha cerca de 7 meses

    Quando seguir: para ver progressive delivery alem do exemplo minimo.

    Validado: descricao cita canary deployments com Argo Rollouts step plugins.

Entrega pratica

Instale Falcon KAC em modo observacao ou politica segura. Converta timeline-mobile-bff mock para Argo Rollout com ALB, metricas de sucesso e rollback automatico. Simule uma versao ruim e documente a linha do tempo de deteccao, pausa e rollback.
