1

A Economia dos Tokens — Por Que Isso Importa

~8 min leitura 3 nervo(s)

Todo token enviado a um LLM custa dinheiro — tanto no input quanto no output. Enquanto os preços de API caíram ~80% de 2025 para 2026, o volume de inferência cresce mais rápido. Agentes de codificação que fazem 50-200 chamadas LLM por tarefa transformam um preço barato por token em um custo caro por tarefa. O problema se complica em três frentes: context bloat (sessões multi-turn acumulam tokens obsoletos), computação redundante (sem caching, o modelo recompute atenção sobre o mesmo prefixo a cada chamada), e hardware subutilizado (configurações default deixam GPUs ociosas).

A tese central: otimização de tokens é um problema de context engineering, não de encurtamento de prompts. A maioria das equipes perde tempo encurtando prompts quando os verdadeiros drivers de custo são context bloat, tool schemas ociosos e histórico de conversação obsoleto.

RTK — O Rust Token Killer (69K+ ⭐)

~10 min leitura 3 nervo(s)

RTK é um proxy CLI escrito em Rust que intercepta comandos shell emitidos por agentes de codificação e retorna output comprimido — mesma informação, muito menos tokens. Com 69K+ estrelas no GitHub, é uma das ferramentas mais populares do ecossistema. O hook do RTK roda como um binário nativo (sem shell bash), reescrevendo transparentemente comandos como git status para rtk git status antes que o agente veja a reescrita.

Quatro estratégias de compressão são aplicadas por tipo de comando: Smart Filtering (remove noise como comentários, whitespace, boilerplate), Grouping (agrupa itens similares), Truncation (mantém apenas contexto relevante), e Deduplication (colapsa linhas de log repetidas). Em um projeto médio TypeScript/Rust, uma sessão de 30 minutos de Claude Code consome ~118K tokens em comandos shell — com RTK, cai para ~23.9K tokens (redução de 80%).

Headroom — Context Compression Layer (39K+ ⭐)

~10 min leitura 3 nervo(s)

Enquanto o RTK foca em comprimir outputs de CLI, o Headroom ataca o problema mais amplo: comprimir tudo que o agente lê antes de chegar ao LLM — tool outputs, logs, arquivos, chunks RAG e histórico de conversação. Criado por Tejas Chopra (engenheiro sênior da Netflix), o Headroom opera como um proxy transparente entre seu app e o provedor LLM, com 3 modos de integração: Library, Proxy e MCP Server.

O pipeline de compressão multi-stage usa: SmartCrusher para JSON (remove chaves redundantes), CodeCompressor para código (AST-aware), Kompress-base para prosa (modelo ML via HuggingFace), e CacheAligner para estabilizar prefixos e garantir KV cache hits. A propriedade chave é CCR (Content-Compressed Retrieval): originais nunca são deletados; o LLM pode buscar a versão completa quando necessário.

Caveman — Output Token Efficiency (72K+ ⭐)

~8 min leitura 3 nervo(s)

O Caveman ataca o lado oposto da equação: enquanto RTK e Headroom comprimem o input (o que o agente lê), o Caveman comprime o output (o que o agente gera). Com 72K+ estrelas, é a skill/plugin mais viral do ecossistema. A premissa é simples: fazer o AI "falar como um cavaleiro" — fragmentos curtos, sem filler, sem "I'd be happy to help" — reduz significantemente os tokens de output.

O projeto tem 3 níveis de intensidade: lite (remove filler, mantém gramática), full (caveman padrão), e ultra (abreviações telegráficas). Benchmarks independentes mostram economia real de 30-50% em uso normal (não os 75% do marketing). Um micro-prompt de 6 linhas (85 tokens) pode superar o skill completo de 552 tokens em tarefas complexas.

LLMLingua — Prompt Compression (Microsoft, 6.2K ⭐)

~10 min leitura 3 nervo(s)

O LLMLingua é a abordagem acadêmica mais madura para compressão de prompts. Publicado no EMNLP 2023 com 6 papers na série, ele usa um modelo de linguagem compacto (GPT2-small, LLaMA-7B) para identificar e remover tokens não essenciais, alcançando até 20x de compressão com perda mínima de performance. A diferença: LLMLingua não reescreve (comosummarization), ele seleciona quais tokens manter com base em perplexidade.

O LLMLingua-2 (ACL 2024 Findings) é 3-6x mais rápido, usando um encoder BERT-level destilado do GPT-4 para classificação de tokens. Integrado ao LangChain e LlamaIndex, funciona como um plugin drop-in para pipelines RAG. O LongLLMLingua (ACL 2024) mitiga o "lost in the middle" e melhora performance RAG em 21.4% usando apenas 1/4 dos tokens.

KV Cache & Prompt Caching — O Segundo Piso de Economia

~10 min leitura 3 nervo(s)

Prompt caching é a otimização de maior ROI para a maioria das equipes. Se o prefixo do seu prompt é byte-a-byte igual a um cache anterior, o provedor reutiliza attention states computados — desconto de 90% no input tokens. O Headroom's CacheAligner separa conteúdo dinâmico (timestamps, user context) do system prompt para manter prefixos cacheáveis estáveis.

No nível de infraestrutura, o KV cache é o gargalo de memória principal. Para um modelo de 30B parâmetros com batch 128 e input 1024 tokens, o KV cache pode ocupar 180 GB. Técnicas como H2O (token eviction), StreamingLLM, SnapKV, e quantização FP8 do KV cache reduzem drasticamente esse overhead. O vLLM e SGLang implementam essas otimizações nativamente.

Inference Engines — vLLM, SGLang, TensorRT-LLM

~10 min leitura 3 nervo(s)

Os três engines de inferência dominantes em 2026 atacam a eficiência em camadas diferentes. O vLLM é o baseline open-source com PagedAttention, continuous batching e prefix caching. O SGLang ganhou o argumento de prefix caching com RadixAttention (reduz TTFT para multi-turn chat). O TensorRT-LLM da NVIDIA extrai máximo throughput com compilação de kernels CUDA fusionados.

Em benchmarks H100 com Llama-3.3-70B: TensorRT-LLM lidera throughput bruto (~2,100 tok/s a 50 req), SGLang tem melhor TTFT para multi-turn com prefixos compartilhados, e vLLM tem a menor barreira de entrada. Para self-hosting, quantização FP8 corta footprint de memória pela metade e dobra velocidade de inferência com perda mínima de acurácia.

Quantização & Model Compression

~8 min leitura 2 nervo(s)

Quantização reduz a precisão numérica dos pesos do modelo de FP16 para INT8, INT4 ou inferior, cortando drasticamente requisitos de memória e compute. Um modelo 70B tem ~280 GB VRAM em FP32, mas apenas ~35 GB em INT4 — redução de 8x em memória. PTQ (Post-Training Quantization) com GPTQ ou AWQ é o ponto de entrada mais comum. O vLLM suporta FP8 nativamente em GPUs Hopper/Ada Lovelace.

Além de quantização de pesos, a quantização do KV cache (FP8, INT4) reduz o memory bottleneck sem retreino. Técnicas como QJL (1-bit) e TurboQuant (ICLR 2026) oferecem compressão extrema com bias zero. A combinação de quantização + sparsity (2:4 pattern) pode dar 30% mais throughput além da quantização isolada.

Context Engineering — O Meta-Skill

~10 min leitura 3 nervo(s)

Context engineering é a disciplina de orquestrar tudo que entra e sai de um LLM para maximizar qualidade e minimizar custo. Não é sobre encurtar prompts — é sobre design de pipeline. O pipeline combinado mais agressivo: Cache prefix (90%) + route to cheapest model (60-95%) + batch non-urgent (50%) + compress prompts (5-20x) + cache responses (100% on repeats) = 95-99% cost reduction vs. naive approach.

As equipes vencedoras em 2026 não são apenas boas em prompts — são boas em context engineering. RTK reduz output de CLI, Caveman comprime linguagem, LSP afina lookup por símbolo, Graphify fornece memória estrutural de longo alcance, e Headroom gerencia o contexto inteiro. Essas abordagens são complementares, não competidoras.
