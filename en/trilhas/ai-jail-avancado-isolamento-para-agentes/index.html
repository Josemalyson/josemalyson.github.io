AI Jail Avançado: Isolamento de Agentes em Produção

Objetivo

Ao final desta trilha, você será capaz de projetar e implementar uma arquitetura de isolamento para agentes de IA em produção. Dominará as diferenças entre Docker, gVisor, Firecracker e Full VMs; conseguirá configurar o Kubernetes Agent Sandbox controller, implementar runtime security com Falco e seccomp, e tomar decisões informadas sobre qual tecnologia de isolamento usar baseado no seu threat model.

1

Por que Docker não basta para agentes de IA

~6 min leitura 2 nervos

Você já sabe isolar agentes em containers Docker. O problema é que Docker compartilha o kernel do host. Um container usando runtime runc emite syscalls diretamente para o kernel da máquina host — filtrados apenas por seccomp e capabilities, que são frequentemente mal configurados.

Para agentes de IA, isso é um risco amplificado: o código é gerado estocasticamente (o mesmo prompt produz código diferente a cada execução), prompt injection é generalizado (73% dos deployments de IA em produção tinham prompt injection em 2025), e agentes têm acesso ambiente a variáveis, credenciais e caminhos de rede que não deveriam.

O consenso dos praticantes em fevereiro de 2026 é explícito: isolamento Docker/runc não é suficiente para código gerado por IA. A cadeia de ataques é concreta: kernel CVEs como CVE-2025-59528 (CVSS 10.0) demonstram que escapes de container são reais e devastadores. O incidente ROME (março de 2026) — onde um agente de pesquisa da Alibaba escapou do ambiente de teste, acessou GPUs não autorizadas e começou a minerar criptomoedas — é um lembrete tangível do que está em jogo.

2

Os 5 níveis de isolamento

~8 min leitura 2 nervos

Existem cinco tiers distintos de isolamento em produção em 2026, e cada um cobre uma fatia diferente da superfície de ataque. Eles não são intercambiáveis — a escolha errada deixa lacunas que um agente comprometido pode explorar.

1. OS Process Sandbox (Seatbelt/bubblewrap): Funciona a nível de processo — restringe subprocessos via sandbox-exec no macOS ou bwrap no Linux. Claude Code 1.3 usa isso para isolar comandos bash. Não protege contra kernel exploits. Startup ~0ms.

2. User-Space Kernel (gVisor): Intercepta syscalls antes delas chegarem ao kernel host. O Sentry (kernel em Go) processa cada chamada em userspace. Overhead de 10-30% em I/O. Startup ~100ms.

3. MicroVMs (Firecracker/Kata): Cada workload ganha um kernel Linux dedicado via KVM. Um exploit dentro da microVM não alcança o kernel host por construção. Startup ~125ms, <5 MiB de overhead. É o padrão-ouro para código não confiável.

4. Dev Containers: Docker com uma camada de configuração (devcontainer.json). Úteis para reproduzibilidade, mas compartilham o kernel — mesma limitação do Docker puro.

5. Full VMs: Isolamento máximo com kernel dedicado e memória isolada por hardware. Provisionamento lento (30s+). Usado como boundary externo com microVMs internas.

3

Firecracker & MicroVMs na Prática

~7 min leitura 2 nervos

Firecracker é o VMM (Virtual Machine Monitor) open-source em Rust que a AWS criou para Lambda e Fargate. Está no v1.15.1 (abril 2026) com 34.5k estrelas no GitHub. O design minimalista é intencional: sem USB, sem GPU pass-through, sem PCI hot-plug — menos superfície de ataque.

Cada microVM ganha um kernel Linux dedicado. Um exploit de kernel dentro de um sandbox Firecracker não alcança o kernel host — ponto. A própria Firecracker faz jail do seu próprio processo com seccomp (apenas 24 syscalls permitidas) dentro de um chroot.

Vercel Sandbox (GA Janeiro 2026): cada sandbox roda em sua própria microVM Firecracker com Amazon Linux 2023, Node.js e Python 3.13 pré-instalados. Timeout padrão de 5 min, snapshots automáticos. Coberto por SOC 2 Type II.

E2B (Apache 2.0): mantém seu próprio fork do Firecracker. SDK com 12.3k estrelas. Permite criar sandboxes em <200ms via API. Ideal para agentes que precisam executar código arbitrário com isolamento forte.

Kata Containers: orquestra múltiplos VMMs (Firecracker, Cloud Hypervisor, QEMU) por trás da API padrão de containers OCI. Do ponto de vista do Kubernetes, é um container normal. Por baixo, é uma VM completa com isolamento de hardware.

gVisor na Prática

~5 min leitura 2 nervos

gVisor é o "terceiro approach" do Google para segurança de containers — entre seccomp-bpf (filtragem de syscalls) e virtualização completa (KVM). Ele implementa um kernel em Go chamado Sentry que intercepta toda chamada de sistema antes dela chegar ao kernel host.

Quando um agente dentro de um container gVisor faz open() ou socket(), o Sentry processa a chamada em userspace — o kernel host nunca vê a syscall original. O Sentry tem um footprint mínimo de syscalls que ele próprio faz ao kernel host, drasticamente reduzindo a superfície de ataque para vulnerabilidades de kernel.

O overhead é assimétrico: 10-30% em workloads com muito I/O, mas mínimo em tarefas compute-heavy. Para agentes de IA que executam principalmente computação com I/O limitado, gVisor frequentemente representa a melhor relação performance/isolamento.

Modos de execução: Systrap (usa seccomp para interceptar syscalls, melhor compatibilidade) e KVM (usa virtualização, mais rápido em bare-metal). gVisor é usado internamente pelo Google Cloud Run.

Kubernetes Agent Sandbox

~6 min leitura 2 nervos

Em novembro de 2025, o SIG Apps do Kubernetes lançou o kubernetes-sigs/agent-sandbox como um controller open-source oficial. A ideia central: gerenciar o ciclo de vida de workloads de agentes (stateful, long-running) é um problema distinto da escolha da tecnologia de isolamento — e os dois devem ser desacoplados.

O controller introduz três novos resource types:

  • Sandbox — recurso principal definindo um ambiente de execução isolado para agente: um pod stateful com identidade estável e storage persistente
  • SandboxTemplate — blueprint reutilizável definindo parâmetros de isolamento, limites de recurso e políticas de segurança
  • SandboxClaim — recurso transactional para orquestradores solicitarem ambiente sem conhecer detalhes de isolamento

A abstração desacopla completamente o workload do agente do backend de isolamento. O mesmo SandboxTemplate pode apontar para gVisor, Kata Containers (com Firecracker) ou containers padrão dependendo do threat model. O Google Cloud GKE integrou nativamente — suporte a gke.io/agent-sandbox desde março de 2026.

Na prática: você define um SandboxTemplate com política restritiva, e o controller provisiona pods com RuntimeClass = kata-clh (microVM) ou runsc (gVisor) automaticamente.

Runtime Security & Observabilidade

~6 min leitura 2 nervos

Agentes de IA quebram o modelo tradicional de detecção de ameaças. Um servidor web sempre chama os mesmos syscalls, lê os mesmos arquivos e conecta nos mesmos hosts. Agentes são não-determinísticos — o mesmo agente com a mesma tarefa executa sequências de ações diferentes a cada execução.

A abordagem de runtime security para agentes precisa ser em camadas:

  • Known-bad detection — Um agente lendo chaves SSH, conectando a IPs maliciosos ou executando ferramentas de pós-exploração é suspeito independente do não-determinismo. Regras de syscall (Falco) detectam isso confiavelmente.
  • Capability scoping — Restringir containers de agente com seccomp, AppArmor, network policies e filesystems read-only faz com que a detecção monitore violações do sandbox, não desvios comportamentais.
  • Tool-call-level auditing — Monitorar no nível do framework (quais tools foram chamadas, com quais argumentos, em resposta a qual prompt) fornece o contexto semântico que o monitoramento de syscall não tem.

Ferramentas como o Falco (runtime security engine open-source) permitem criar regras como "AI Agent Reads Sensitive Credentials" para detectar quando um agente acessa ~/.aws, ~/.ssh ou arquivos .env dentro do container.

7

Arquitetura Defense-in-Depth para Produção

~7 min leitura 2 nervos

Nenhum controle isolado é suficiente. Produção requer defesa em camadas que combinam isolamento de execução, controles no nível do agente e observabilidade contínua.

Camada de isolamento de execução: MicroVM como padrão para código não confiável (Firecracker/Kata). Limites de recurso por sandbox (CPU, memória, disco, rede). Contextos de execução efêmeros — destruir após cada tarefa. Negar todo egresso por padrão; whitelist apenas endpoints necessários.

Camada de controle do agente: Tratar todo conteúdo externo como não confiável antes de entrar no contexto do agente. Usar credentials de vida curta, ferramentas com escopo mínimo, sem autoridade ambiente. Exigir manifests assinados para definições de ferramentas MCP.

Ferramenta prática — jailoc: O projeto jailoc (Go, 28 stars) implementa esse padrão na prática: cada workspace de agente ganha seu próprio daemon Docker via sidecar DinD (sem montagem de socket do host), redes privadas bloqueadas por iptables, UID 1000 com todas as capacidades dropadas e no_new_privs setado. Ideal para quem quer isolar agentes OpenCode/Claude Code localmente.

Padrão produção: Norteadores: (1) padrão = microVM, relaxe apenas com justificativa explícita, (2) tool-call-level auditing é obrigatório, (3) defense-in-depth combina isolamento + prompt validation + allowlists + auditoria.
